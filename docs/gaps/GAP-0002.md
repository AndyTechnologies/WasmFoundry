# GAP-0002 — Compiler binary version not in build cache fingerprint (v1)

## Context

The build cache fingerprints the manifest, toolchain cache key, WasmFoundry version,
source bytes and dependency fingerprints. It does **not** fingerprint the native compiler
binary (clang, asc, rustc) or its standard libraries.

## How it was discovered

While designing the fingerprint composition (ADR-0001, `plan.md` #68), the plan lists
"toolchain version" as a fingerprint input but the toolchain trait exposes `cache_key()`
which returns a textual invocation contract — not a binary version query. Detecting
native compiler versions would require running `clang --version`, `asc --version`,
`rustc --version` for every build, which adds process overhead and platform-specific
parsing to a fingerprint that should be cheap and portable.

## Impact

Upgrading a native compiler (e.g. installing clang 16 → 17) silently reuses stale
artifacts from the old compiler. The user must run `rm -rf target/` to force a clean
rebuild after a toolchain upgrade.

## Does it block the current milestone?

No. The cache is content-based: it works correctly for the vast common case (no compiler
upgrade between builds). The gap is a known escape hatch (clear `target/`).

## Options

1. **Query compiler version per build** — adds `std::process::Command` calls for every
   module's fingerprint computation. Fragile parsing of `--version` output.
2. **Hash compiler binary** — `sha256sum $(which clang++)` per build. Slow and
   unreliable (the binary may move between versions).
3. **Defer to v2** — keep the escape hatch (clear `target/`) and add version fingerprinting
   when the cache surface grows (e.g. when a remote cache or CI pipeline demands it).

## Decision

Defer to v2 (option 3). The cache is a local optimisation; `target/` is ephemeral by
convention. A user who upgrades a compiler should clear it.

## Consequences

- The cache is correct for unchanged compilers and degrades gracefully when the compiler
  changes (stale artifact is produced but is valid wasm for the new compiler target).
- Documentation must state the escape hatch (see README, ADR-0001).
- A future cache v2 may add a `--clean` flag that clears `target/wf/cache.toml` without
  removing the artifacts themselves.

## Affected tests

The cache tests (`crates/wf-toolchains/src/cache.rs`, `crates/wf-cli/src/build.rs` unit
tests, `crates/wf-cli/tests/rust_project.rs` e2e tests) do not exercise compiler
upgrades; they would be impossible to test without controlled binary substitution.

## Affected documentation

- `docs/adr/0001-cache-fingerprint-blake3.md` — records this as the v1 limitation.
- `README.md` — may note the cache behaviour under the Status section.
